# /redloop — автономная работа, которая доходит до конца

База: `~/.claude/skills/redloop`. Спека — `DESIGN-redloop-v2.md` (прошла plan-panel v1 → NEEDS-WORK@0.86,
все 6 critical закрыты в v2). Контракт журнала — `EVENTS-CONTRACT.md`.

## Принцип
Автономность делает не «сильный промпт», а петля `prompt → verify → retry → stop`, у которой
стоп-условие проверяется командой, а не прозой. Промпт — один из элементов петли, не она сама.

## Поток (6 стадий)

### S1. RECON
```bash
bash ~/.claude/skills/redwork/lib/risk-classify.sh <changed_files_or_/dev/null> --tags "<теги>"
```
+ определить проект (project-map / CLAUDE.md проекта) и тип работы (code / content / research / infra).
**NO-GO — штатный исход.** Если оверхед S1–S3 дороже задачи (меньше ~15 минут работы) или результат
принципиально непроверяем — сказать прямо: «автономка тут дороже пользы, делаю обычным ходом»
и выйти. Не заряжать автономку ради автономки.

### S2. CONTRACT — гейт старта
Собрать `contract.json`:
```json
{ "task": "...", "runner": "loop|redwork|workflow|session",
  "scope_globs": ["src/**"], "budget": {"max_iters": 12, "max_minutes": 90},
  "thresholds": {"stall": 3, "loop": 3}, "escalation_channel": "tg:attunedbot",
  "project_root": "/абсолютный/путь/к/проекту",
  "state_files": ["PLAN.md", "state.json"],
  "fresh_check": {"kind": "finalize|plan-panel|artifact-pass", "required": true},
  "dod": [{"id":"t","cmd":"npm test","expect_exit":0},
          {"id":"card","cmd":"grep -q wb-pr- src/x.css","expect_exit":0,"weak":true},
          {"id":"n","cmd":"test $(grep -c \"шаг('\" a.ts) -ge 43","expect_exit":0,"weak":true,"baseline":40}],
  "human_acceptance": [
    {"id":"52","what":"карточка программы","probe":"card"},
    {"id":"57","what":"конструктор без программ","manual_only":true,"why":"вкусовой кадр"}],
  "acceptance_optout_why": "нужно только если human_acceptance = [] (кадров нет вовсе)",
  "mode": "autonomous | assisted" }
```
**Четыре правила v3.3 — прямое следствие разбора прогона 2026-09-03** (закрылся «зелёным»,
свежий `/finalize` дал NEEDS-WORK, два кадра приёмки из девяти не тронуты вообще):
- `fresh_check` — свежий чекер объявлен машинно. Отказ возможен, но с `why`.
- `human_acceptance` — **обязательное поле** и **список**, а не строка прозы. У пункта либо
  `probe` (id существующей строки DoD), либо `manual_only + why`. Пункт без того и другого —
  способ потерять кадр молча; отсутствие поля целиком — способ воспроизвести инцидент удалением
  строки, поэтому осознанный отказ пишется как `[]` + `acceptance_optout_why`.
  С v3.3.3 у поля есть **читатель в журнале**: приёмка снимается снапшотом в `run_start`
  (машинные поля `id/probe/manual_only`), а `run_done` требует `acceptance_presented[]` со ВСЕМИ
  `manual_only`-id — иначе отказ `acceptance_not_presented`. Контракт без поля или прозой
  не стартует вовсе (`acceptance_not_declared` / `acceptance_not_itemized`) — гейт стоит на
  старте, чтобы не превратиться в ловушку на финале.
- `weak: true` — признание, что проба смотрит на строку в файле (`grep`/`test`), а не на
  поведение. Контракт из ОДНИХ слабых проб отвергается целиком (`all_probes_weak`).
- `baseline` — порог вида `-ge N` считается от факта на старте. Без него «43» — просто число,
  в которое упрутся впритык (порог `-ge 0` факта не требует: он ничего не утверждает).
- `project_root` — **абсолютный** путь: относительный резолвится от вызывающего, и гейт с
  раннером молча смотрели бы в разные каталоги.
⚠ Снапшот `run_start` собирается **только из `contract.json`**. Те же поля, присланные раннером
в payload, отвергаются (`snapshot_override_attempt`): раннер — та сторона, за которой ведётся
надзор, и `run_start '{…,"human_acceptance":[]}'` снимал гейт тридцатью символами.

`mode` — кто задаёт темп. `assisted` ставится, когда владелец ведёт сессию сам и пишет промпты
руками: тогда детекторы темпа молчат, а прогон не идёт в знаменатель калибровки автономности.
Читается из журнала (снапшот `run_start`), а не из `contract.json` на лету — правка контракта
задним числом надзор не отключает.
```bash
bash lib/contract-lint.sh <run_dir>/contract.json
```
Гейт **fail-closed**: <80% строк DoD исполнимы командой, нет числовых порогов, нет scope, нет канала
эскалации, нет `fresh_check`, приёмка прозой, непризнанная слабая проба, порог без `baseline`,
нет `project_root` под внешнее состояние → старт запрещён. Тогда — ОДИН батч вопросов (`AskUserQuestion`, ≤4). Не влезло в 4 вопроса →
задача не готова к автономке → NO-GO, а не «спрошу потом».
**Не-кодовая работа** проверяется командами над артефактом (файл непуст, JSON валиден по схеме,
элементов ≥N, ссылки резолвятся, `redtone check`). Вкусовое качество в DoD не идёт — оно уходит
в `human_acceptance` явно.

### S3. COMPILE
```bash
bash lib/compile.sh <run_dir>/contract.json <run_dir> --profile code|content|research|infra
```
Собирает `prompt.md` из `patterns/` (бюджет 6000 токенов; обязательные — P-STATE, P-EXIT, P-NOASK,
P-UNTRUSTED — входят всегда; остальные по success_rate; новый приём стартует с 0.5) и штампует
`patterns_sha` в контракт. Промпт показать владельцу перед запуском.

### S4. LAUNCH
| Случай | Раннер |
|---|---|
| код→прод, проект прошёл `/redwork-init` | `redwork` **режим 2** |
| просят режим 3 | ⚠ Phase B/C redwork не построены → режим 2 + сказать об этом вслух. Молча mode 3 не пытаться |
| многошаговая не-код работа | `/loop` (dynamic) + внешнее состояние |
| широкий фан-аут | `Workflow` |
| прочее | одиночная длинная сессия с P-STATE |
Проект не прошёл онбординг redwork → вести на `/redwork-init`, гейт не обходить.
Перед стартом сверить `patterns_sha` контракта с текущим (`lib/patterns.sh sha`): разошлось из-за
карантина приёма или правки autonomy-gate → перекомпилировать, не стартовать замороженным снапшотом.

### S5. WATCH
Прогон пишет журнал (`lib/events.sh append`, единственный писатель — сессия).
**Каждая итерация обязана дать `iter_done`** — иначе `run_done` будет отвергнут кодом 4
(`reason=no_iterations_logged`). Со ВТОРОЙ итерации журнал требует внешнего состояния на диске
(`state_files_missing`), а финал — зелёной подписи свежего контекста:
`check_result` с `check_id: fresh_check`, полем `verdict` из списка `fresh_ok_verdicts` (сейчас `SHIP`/`PASS`) <!-- fresh_ok_verdicts: SHIP PASS --> **и полем
`report`** — путём к отчёту чекера (существует, непуст, лежит под каталогом прогона/проекта,
новее последней итерации; вердикт сверяется с телом отчёта, sha256 журнал считает сам).
Подпись протухает после следующей итерации (`fresh_check_stale`). ⚠ Отчёт всё равно пишет
та же машина — это защита от небрежности, а не от подлога. Отказ по политике пишется в журнал
событием `runner_error/journal_policy_reject`, а не остаётся тишиной. Число итераций в финале **считает журнал**,
самоотчёт раннера едет рядом как `iters_claimed`. Это не придирка: два первых живых прогона дали 5 и 3 события
на 22 и 19 итераций, и детекторы весь прогон были слепы. Проверка, упёршаяся во внешнее
(нет токена, снят доступ), пишется как `check_result` с `result: blocked_by_env` или
`blocked_owner_action` — она не красная и не зелёная, и владелец увидит её отдельным сигналом.
Машинно непроверяемые кадры приёмки (`manual_only`) закрываются только предъявлением владельцу
поимённо: их id перечисляются в `acceptance_presented[]` внутри `run_done`. Журнал сверяет
**покрытие**, а не факт того, что владелец посмотрел, — это защита от молчаливой потери кадра,
не доказательство приёмки.
**Не получилось — тоже финал.** `run_done` с `outcome` из `failed`/`blocked`/`abandoned` <!-- run_done_outcomes: success failed blocked abandoned -->
записывается без подписи чекера и без предъявления кадров: провал обязан остаться фактом
журнала, а не тишиной. Умолчание `success` означает заявку на успех со всеми гейтами.
Детекторы:
```bash
bash lib/detect.sh scan <run_dir>
```
STALL · LOOP · RETRY-BURN · DRIFT · PREMATURE-EXIT · ASK-STORM · BUDGET-OVERRUN ·
BLOCKED-EXTERNAL · **FRESH-CHECK-MISSING** · **ITERS-MISMATCH** · **POLICY-REJECT**
(SILENCE — внешний сторож по heartbeat). Три последних — второй невод под жёсткими гейтами
журнала: они видят прогоны со `strict=0` и прогоны, разобранные постфактум чужой сессией.
**`FRESH-CHECK-MISSING` не тихий по умолчанию** — список не-тихих лежит в `lib/constants.json`
(он в git), а не в `stats/detectors.json` (он в .gitignore и до чужой установки не доезжает).
Он не прокси, а детерминированный факт — прогон закрыт, чекер требовался, зелёной подписи нет; самоизлечения
у него не бывает, а в shadow он бесполезен, потому что ловит именно обход гейта.
Детекторы изолированы друг от друга: падение одного даёт отдельный сигнал `DETECTOR-BROKEN`,
а не молчание всего разбора.
**Все детекторы стартуют в shadow**: пишут события, но НЕ будят человека. Выход из shadow —
`lib/detect.sh calibration`: FP-rate <10% на ≥5 живых прогонах, флип руками в `stats/detectors.json`.
Сработал не-shadow детектор → эскалация:
```bash
bash lib/escalate.sh <run_dir> STALL "unblock,review" "<диагноз>" "<что предлагаю>"
```
Финал прогона (`RUN_DONE`) идёт тем же каналом: молчание не считается успехом.

### S6. POSTMORTEM
Посчитать intervention rate (сколько раз человек вмешался), итерации до зелёного DoD, сработавшие
детекторы. Записать применения приёмов и наблюдения:
```bash
bash lib/patterns.sh record P-EXIT <run_id> ok <project> <task_type> <session_id>
bash lib/patterns.sh candidate <slug> <run_id> <project> <task_type> <session_id> "<наблюдение>"
bash lib/patterns.sh promotable      # ≥2 НЕЗАВИСИМЫХ подтверждения → показать владельцу на ревью
bash lib/patterns.sh demote-scan     # success_rate<50% на последних 5 → в patterns/quarantine/
```
Приём становится правилом только после ревью текста человеком. Единичное наблюдение всё равно
видно владельцу в отчёте прогона — просто не становится правилом само.


## Карточка прогона (обязательный вывод)

Каждый переход между стадиями сопровождается перерисовкой карточки в чате. Не рисовать её руками —
она **генерируется из фактов прогона**, иначе рано или поздно покажет то, чего в журнале нет:

```bash
python3 lib/dashboard.py <run_dir> --stage S3
```
Вывод — HTML-фрагмент, отдать его в `mcp__visualize__show_widget` (title вида `redloop_run_<slug>_<stage>`).
Показывать: сразу после S2 (контракт собран), после S3 (промпт собран), при запуске S4, дальше между
итерациями S5 (или по `/redloop-status`), и финальную — на S6.

Что в карточке: полоса стадий S1–S6, прогресс контракта (зелёных проверок из скольких, с именами
команд), **приёмка человеком — «предъявлено владельцу N из M» с построчным статусом**, итерация
из бюджета, вмешательства человека, допущения, разбивка «инфра-сбои / красные вердикты»,
сработавшие детекторы с пометкой тихого режима.

Правила, которые нельзя нарушать при правке генератора:
- **Не досочинять.** Нет источника — «—» с причиной, а не правдоподобная цифра.
- **Знаменатель обязателен** у каждого счётчика: «4 итерации» без «из 12» — это не прогресс.
- Детектор в shadow подписан «тихий режим»: карточка не должна выглядеть тревогой, если человека
  никто не будит.
- Красный вердикт и инфра-сбой показываются РАЗНЫМИ числами — это разные болезни.

## Границы (жёсткие)
- **Floor снаружи промпта.** P-NOASK намеренно глушит «спроси человека», поэтому необратимое
  (деньги, секреты, миграции, auth, публикация, удаление) блокирует внешний машинный гейт
  (`redwork/lib/risk-classify.sh` + `autonomy-gate.sh`), а не текст промпта.
- **Триггер — только явная фраза владельца.** Авто-детект «эта задача просится в автономку» —
  максимум предложение одной строкой, никогда самозапуск.
- **Не обходит гейты redwork/PROD-SAFETY.** redloop заряжает их, а не заменяет.
- **Текст приёмов — в git; счётчики — вне git** (`stats/`, `.gitignore`), local-only.
- **`DRIFT` по-прежнему self-report.** Детекторы считает сама сессия; внешний сторож
  (`com.redloop.watch`, см. ниже) появился в v3.1 и ловит тишину, но выход за scope ловится
  только если раннер честно шлёт `out_of_scope`. Машинный расчёт из `git diff --name-only`
  против `scope_globs` — остаток Ф2, и говорить об этом прямо, а не подразумевать.

## Внешний сторож
`lib/watch.sh` — джоба `com.redloop.watch` (launchd, каждые 15 минут, заведена в `redjob`).
Обходит реестр, читает журналы, пишет тревоги в `runs/<id>/alerts.jsonl` и шлёт в TG те детекторы,
что выведены из тихого режима. `SILENCE` выведен намеренно (три прогона подряд закончились
тишиной), но эскалирует только если внешних признаков жизни в проекте нет — иначе тревога
подавляется и считается отдельно. Проверить руками: `bash lib/watch.sh --dry-run`.

## Общий словарь
`lib/constants.json` — зелёные вердикты чекера, ВСЕ известные вердикты, его `check_id`, виды
чекера, умолчание `state_files` и список детекторов, не тихих по умолчанию. Потребителей
**пять**: `events.sh`, `detect.sh`, `dashboard.py`, `contract-lint.sh`, `compile.sh`.
Читается **fail-closed** всеми: нет файла или он неполон → журнал отказывается писать, скан
отдаёт `CONSTANTS-MISSING` (он есть в enum эскалации — иначе тревога была бы немой),
карточка пишет об этом строкой, линт отказывает, набор тестов краснеет.
⚠ Выкат: файл обязан ехать в установку ВМЕСТЕ с кодом — от него зависит каждая запись журнала.

⚠ В зелёных вердиктах только длинные однозначные метки (`SHIP`, `PASS`). Короткий `OK` был
дырой: вердикт ищется в теле отчёта, и «всё OK по стилю, но 3 critical» закрывало прогон
зелёным. Вердикт берётся из МАШИННОГО артефакта (`judge.json` рядом с отчётом или сам
отчёт-JSON), и только при его отсутствии — из объявления в тексте: разбор человеческой прозы
трижды подряд давал то ложный пропуск, то ложный отказ (37% честных отчётов отвергались).
⚠ Регистронезависимость на кириллице зависит от локали: у джоб `LANG` пуст, и `grep -i`
не сложил бы «Вердикт» с «вердикт». Регистры выписаны явно — не заменять обратно на `-i`. Читают ТРОЕ: `events.sh` (гейт), `detect.sh` (детектор), `dashboard.py` (карточка).
