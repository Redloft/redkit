# redloop — EVENTS-CONTRACT v3.3.6

Единственный интерфейс между тремя раннерами (redwork / `/loop` / Workflow / одиночная сессия)
и детекторами. Детекторы НЕ читают транскрипт, НЕ парсят вывод модели — только этот журнал.
Действие рождает событие: **panel-critical #1**.

## Файл и права
- Путь: `runs/<run_id>/events.jsonl`, append-only, одна JSON-строка на событие.
- **Единственный писатель — сессия прогона** (через `lib/events.sh append`, `O_APPEND` + lock).
  Внешний сторож (`redjob`) **только читает** journal + mtime и пишет свои алерты в
  СВОЙ файл (`runs/<run_id>/alerts.jsonl`). Асимметрия прав снимает конфликт ops↔backend.
- Ротация запрещена, пока `phase != DONE`.

## Схема (обязательные поля каждого события)
```
{ schema_version: 1, ts: "<ISO8601 UTC>", run_id, seq: <int, монотонный>,
  event_type: <enum>, kind: "progress"|"infra_failure"|"negative_verdict"|"blocked",
  severity: "info"|"warn"|"critical",
  denominator: { iter: <int>, of: <int|null> },     # ⚠ знаменатель ОБЯЗАТЕЛЕН
  payload: { ... }                                   # типизирован per event_type
}
```
`kind` — тот самый нерасщеплённый шов: **«раннер упал» ≠ «раннер честно вернул отрицательный
вердикт»**. `infra_failure` (таймаут, OOM, обрыв, exit≠0 самого раннера) → ретрай уместен.
`negative_verdict` (тест красный, judge=FIX-FIRST, DoD не сошёлся) → ретрай БЕСПОЛЕЗЕН без
изменения подхода: считается в LOOP-детекторе, а не в infra-ретраях.
`blocked` (v2) — третье состояние, найденное на живых прогонах: проверка упёрлась во ВНЕШНЕЕ
(нет токена, доступ снят, чужой сервер отдаёт статику мимо нашего конфига). Не красная и не
упавшая: действие за владельцем. Не зелёная тоже — DoD не закрыт.

⚠ **kind выводится ТОЛЬКО в `events.sh`, ровно в одном месте.** Порядок: сначала `result`
(закрытый enum `blocked_by_env` | `blocked_owner_action`) → `blocked`; иначе `exit_code==0`
→ `progress`; иначе `negative_verdict`. Детекторы читают `kind` и НЕ парсят префиксы payload:
правило, живущее в двух местах, разъезжается — это уже стоило скиллу трёх немых детекторов.

## Запрещено в журнале (наследуется от redwork)
Нет `stdout`/`stderr`/`raw`/`output`, нет текста задачи, нет PII, нет значений секретов.
Только структурный summary и хеши. Каждый append проходит `secret-guard`.

## Потребители (у каждого сигнала есть адресат — иначе сигнала нет)
| Сигнал | Потребитель |
|---|---|
| `detector_fire` (shadow=false) | `lib/escalate.sh` → TG @Attunedbot Игорю |
| `detector_fire` (shadow=true) | только `runs.jsonl` + отчёт калибровки, НЕ будит человека |
| `run_done` | TG-карточка итога + `postmortem.sh` → ledger |
| `human_acceptance` (снапшот `run_start`) | гейт `run_done` (`acceptance_not_presented`) + блок карточки «предъявлено владельцу N из M» |
| `acceptance_presented[]` (в `run_done`) | тот же гейт (сверка покрытия) + карточка: у каждого кадра видно, предъявлен он или нет |
| `heartbeat` stale | внешний сторож redjob → TG (детектор тишины сам обязан быть не-тихим) |

## Режим прогона (v3.1)
`contract.json` → `mode: "autonomous" | "assisted"` (по умолчанию `autonomous`), снимается
в `run_start`. **`assisted` — темп задаёт человек**: он пишет промпты сам, а сессия работает
между ними. Для такого прогона детекторы темпа (`STALL`, `SILENCE`) выключены: пауза означает,
что человек занят, а не что агент завис. Судить их той же меркой = гарантированные ложные тревоги.
Калибровка считает `runs_autonomous` и `runs_assisted` раздельно: порог выхода из тихого режима
опирается только на автономные прогоны, иначе парк разбавляется тем, что автономностью не было.

## Реестр прогонов (v3.1)
Прогоны живут где угодно: `~/.claude/skills/redloop/runs/<id>` и `<проект>/.redloop/runs/<id>`.
`run_start` регистрирует прогон в `runs/index.jsonl` (путь + run_id + задача, идемпотентно).
Калибровка и внешний сторож ходят по РЕЕСТРУ, а не по одному каталогу: пока считали по каталогу,
третий живой прогон был невидим, и порог «5 прогонов до выхода из тихого режима» набрался бы
по неполному парку. Нечитаемые каталоги считаются отдельным числом (`unreadable`), а не молчат.

## Политика записи (v2) — то, чего не даёт просьба в промпте

Два живых прогона дали 5 и 3 события на 22 и 19 итераций: пять детекторов из шести читают
`iter_done`/`check_result`, им было нечего читать. Просьба в промпте это не лечит, поэтому:

- **`run_done` без единого `iter_done` отвергается** (`exit 4`, `reason=no_iterations_logged`).
  Финал без итераций означает, что сторож был слеп весь прогон.
- **Финал объявляется один раз.** Повтор с ТЕМ ЖЕ payload — no-op с предупреждением (ретрай
  раннера безопасен). Повтор с ДРУГИМ payload → `exit 4`, `reason=run_done_already_recorded`:
  продолжение работы после финала — это новый `run_id`.
- **Строгость фиксируется в `run_start`** (`strict_journal`) и дальше читается ИЗ ЖУРНАЛА.
  Журнал есть, а поля нет → прогон стартовал до выката v3 и доживает по старым правилам
  (`strict=0`); иначе обещание «идущий прогон не потеряет финал» было бы ложным.
  Журнала нет вовсе и приходит `run_done` → это ноль итераций, самый слепой случай:
  политика применяется, отказ `no_iterations_logged`.
  Рубильник: `REDLOOP_STRICT_JOURNAL=0` на старте прогона.
- **`_policy_check` читает журнал ДО взятия лока.** Это осознанно и безопасно ровно потому,
  что писатель по контракту один (сессия прогона); при двух писателях здесь был бы TOCTOU.
  Инвариант single-writer — предусловие политики, а не деталь реализации.
- **Бюджет снимается снапшотом в `run_start`** из `contract.json`. Детектор бюджета остаётся
  чистой функцией от журнала и не лезет во второй файл.

### Ужесточения v3.3 — разбор прогона 2026-09-03

Прогон закрылся `verdict: green` на 6-й итерации из 12; `/finalize` по тому же диффу, запущенный
владельцем через 2 ч 45 мин, дал **NEEDS-WORK** (валидация контакта разошлась с каналом; кнопка
«поделиться» отдавала поддельную бронь на живом домене). Два кадра приёмки из девяти
(«сочетаемость», «конструктор без программ») не были тронуты вообще: под них не было пробы.
`PLAN.md` и `state.json` не появились в проекте ни разу. Отсюда три правила:

- **И7 · внешнее состояние.** Со ВТОРОЙ итерации `iter_done` без файлов из `state_files`
  (умолчание `PLAN.md`, `state.json`, адрес — `project_root`) отвергается: `exit 4`,
  `reason=state_files_missing`. То же проверяется на `run_done`. Файл СТАРЕЕ старта прогона
  не засчитывается — иначе зачтётся чужой артефакт (урок `verify-artifact-freshness`).
  Осознанный отказ — `"state_files": []` в контракте. Рубильник: `REDLOOP_STATE_FILES_ENFORCE=0`.
- **И8 · финал подписывает свежий контекст.** Если `run_start` снял `fresh_check.required=true`,
  `run_done` требует последнего `check_result` с `check_id: fresh_check`, `exit_code: 0` и
  `verdict` из `fresh_ok_verdicts` словаря (сейчас `SHIP`, `PASS`; `GREEN`/`OK` сняты — они находятся в любом человеческом тексте) <!-- fresh_ok_verdicts: SHIP PASS -->. Нет события → `reason=fresh_check_missing`; вердикт
  NEEDS-WORK/FIX-FIRST (даже при `exit 0`) → `reason=fresh_check_not_green`.
  Прогон, стартовавший до v3.3 (в `run_start` нет `fresh_check`), доживает по старым правилам.
- **И5 · число итераций считает журнал.** `iters` в `run_done` пересчитывается из событий
  `iter_done`; самоотчёт раннера сохраняется как `iters_claimed`, расхождение помечается
  `iters_mismatch: true` и поднимает `severity` до `warn`. Живые прогоны рапортовали 13 и 19
  итераций при НУЛЕ событий `iter_done` — «сколько он работал» нельзя было проверить вообще.

### Ужесточения v3.3.1 — по вердикту FIX-FIRST панели на v3.3

Свежий чекер нашёл в самих гейтах пять critical. Классы, а не опечатки:

- **Сверка enum'а регуляркой = отсутствие сверки.** `grep -qw "$verdict"` пропускал `verdict=".*"`,
  и гейт И8 обходился двумя символами. Теперь точное сравнение со списком (`_in_list`), и тот же
  список читается ВСЕМИ тремя потребителями из `lib/constants.json`: гейтом, детектором и карточкой.
  Дублировать его снова нельзя — именно дубль дал дефект, когда карточка считала зелёным
  `fresh_check` с вердиктом NEEDS-WORK.
- **Секрет-гард обходился вторым писателем.** Снапшот из `contract.json` дописывался в payload
  ПОСЛЕ `kw_secret_found`. Теперь гард гоняется второй раз по ИТОГОВОМУ payload, а из
  `fresh_check` в журнал едут только машинные поля `{kind, required}` — свободный текст `why`
  остаётся в контракте.
- **Самоаттестация свежего чекера.** Событие требовало только слова `verdict`. Теперь обязателен
  `report` — путь к отчёту чекера: файл существует, непуст, лежит ПОД каталогом прогона или
  проекта, создан ПОСЛЕ последней итерации; вердикт события сверяется С ТЕЛОМ отчёта
  (`fresh_check_verdict_mismatch` при расхождении), `report_sha` считает сам журнал.
  ⚠ Граница честности: отчёт пишет та же машина, что и патч. Это защита от небрежности и
  рассинхрона, не от подлога. Формулировку «выдумать вердикт нельзя» из доки убрали как ложную.
- **Протухшая подпись** (`fresh_check_stale`): зелёный чекер, после которого была ещё одна
  итерация, финал не закрывает — схема iter → SHIP → iter → run_done проходила гейт.
- **Отказ по политике был тишиной.** `_reject` теперь пишет `runner_error` с
  `error_class: journal_policy_reject` и машинной `reason` ПЕРЕД возвратом кода 4 — «пытался
  закрыться и не смог» стало фактом журнала, у которого есть детектор `POLICY-REJECT`.
- **Внешнее состояние ужесточено:** пустой файл не состояние; путь обязан лежать под
  `project_root` (абсолютный путь наружу и `..` отвергаются); отсутствие `project_root`
  в снапшоте — отказ, а не тихий фолбэк на каталог прогона (иначе гейт зеленел бы на чужих файлах).

### Ужесточение v3.3.3 — И9 · у приёмки человеком появился читатель

До этой версии `human_acceptance` был обязательным полем гейта контракта и печатался в промпте —
и на этом всё. Ни `run_start` его не снапшотил, ни `run_done` не нёс следа, ни карточка о нём
не знала. То есть кадр приёмки доходил до владельца **прозой в ответе агента, которую никто не
сверял со списком** — ровно тот класс «сигнал без читателя», из-за которого 03.09 два кадра из
девяти («сочетаемость», «конструктор без программ») не были тронуты вообще.

- **Снапшот в `run_start`.** Приёмка снимается машинными полями `{id, probe, manual_only}`.
  Свободный текст `what`/`why` остаётся в контракте: снапшот дописывается ПОСЛЕ первого прогона
  секрет-гарда, и пускать туда произвольный текст — тот же обход, что был закрыт у `fresh_check.why`
  и у текста задачи в реестре. `id` может отсутствовать — тогда адресом становится позиция (`#0`):
  безымянный пункт всё равно обязан быть предъявляемым.
- **Гейт стоит на `run_start`, а не на финале.** Контракт без `human_acceptance` → отказ
  `acceptance_not_declared`; приёмка прозой (не массив) → `acceptance_not_itemized`. Оба чинятся
  правкой контракта и повтором `run_start`. Ставить эту проверку на `run_done` было нельзя:
  снапшот неизменяем, и прогон, отработавший часы, не смог бы закрыться уже никогда — гейт стал бы
  ловушкой, а не гейтом.
- **Покрытие проверяется на `run_done`.** Каждый пункт с `manual_only: true` обязан быть назван
  в `acceptance_presented[]` (массив строк-id). Нет поля → `acceptance_not_presented`; названы не
  все → та же причина с перечислением недостающих; назван id, которого нет в приёмке контракта →
  `acceptance_presented_unknown` (описка не должна закрывать знаменатель чужим числом).
- **Карточка — второй читатель.** Блок «предъявлено владельцу N из M» с построчным статусом:
  у пунктов с `probe` — состояние соответствующей строки DoD, у `manual_only` — предъявлено/нет.
  Снапшота нет вовсе → «—» с причиной (прогон стартовал до выката), а не бодрое «0 из 0».
- Рубильник: `REDLOOP_ACCEPTANCE_ENFORCE=0` (рантайм; за гейт контракта по-прежнему отвечает
  `REDLOOP_ACCEPTANCE_STRICT`).

⚠ Граница честности: журнал проверяет, что кадр **назван**, а не что владелец его **посмотрел
и принял**. Это защита от молчаливой потери кадра, не доказательство приёмки.

### Ужесточения v3.3.4 — свежий чекер нашёл шесть critical в самих гейтах И9/И8

Четвёртый круг панели. Классы, а не опечатки:

- **Сверка вердикта шла по НАЧАЛУ строки — и отвергала каждый честный отчёт.** Настоящий
  `judge.md`, который пишет `/finalize`, объявляет вердикт в СЕРЕДИНЕ строки:
  `` run_id: `x`  verdict: **SHIP**  confidence: 0.94 ``. Якорь `^` его не брал, и ни один прогон
  с реальным чекером закрыться не мог; зелёными были только синтетические фикстуры
  (`verdict: **SHIP**` с начала строки) — тест шёл не тем путём, что система. Последствие
  хуже пропуска: единственным способом закрыть честный прогон становилась дописка строки
  в отчёт руками, то есть гейт подталкивал ровно к подлогу, от которого защищает.
  Теперь якоря нет, распознаются `**verdict**:`, `- Вердикт — X`, объявление в середине строки,
  а в набор тестов добавлен позитивный контроль на артефакте РЕАЛЬНОГО формата.
- **Внутри найденной строки сверка оставалась подстрочной.** `Вердикт: это НЕ SHIP` + событие
  `verdict: SHIP` проходили. Класс не был устранён — он переехал из тела отчёта в строку
  объявления. Теперь из строки вырезается ТОКЕН сразу после разделителя и сравнивается точно
  тем же `_in_list` со списком `fresh_verdict_all`; метка вне enum — отказ, две разные метки — отказ.
  ⚠ Кириллица в шаблонах пишется полной альтернацией (`вердикт|Вердикт|ВЕРДИКТ`), а не через
  `[Вв]ердикт`: bracket-выражение над многобайтным символом в C-локали распадается на байты.
- **Раннер снимал надзор одним полем в payload.** `run_start '{…,"human_acceptance":[]}'`
  затирал снапшот контракта, `need=0`, финал проходил с нулевым покрытием — а карточка при этом
  УТВЕРЖДАЛА «кадров приёмки нет, осознанный отказ владельца». Поля надзора
  (`human_acceptance`, `fresh_check`, `state_files`, `project_root`, `budget`, `mode`,
  `strict_journal`) теперь берутся ТОЛЬКО из `contract.json`, а их появление в payload `run_start`
  отвергается как `snapshot_override_attempt` — молча игнорировать мало, иначе раннер считал бы,
  что поле применилось.
- **Гейт был fail-OPEN там, где вся база fail-closed.** (а) Проверка объявления висела на
  `[ -f contract.json ]`: прогон без контракта в каталоге стартовал с нулевым покрытием —
  теперь это `acceptance_not_declared`. (б) Приёмка массивом СТРОК (проза, разложенная по
  пунктам) проходила `type=="array"`, снапшот падал в `null`, гейт выключался ровно на том
  входе, ради которого заведён — теперь элементы обязаны быть объектами
  (`acceptance_not_itemized`).
- **Гейт стоял на необязательном шаге.** И7/И8/И9 читают требования из снапшота `run_start` —
  а сам `run_start` никто не требовал: прогон, не позвавший его, закрывался зелёным в обход
  ВСЕЙ политики. Теперь финал без `run_start` в журнале — `run_start_missing`.
- **Промпт и журнал звали кадр разными адресами.** `compile.sh` считал id своей формулой
  (`.id // "?"`), журнал — позиционной (`#N`), и предъявление безымянного кадра отвергалось как
  описка. Плюс сломанное экранирование печатало НЕВАЛИДНЫЙ JSON
  (`acceptance_presented: [53", "57]`) — единственный машинный инструктаж по новому
  обязательному полю был заведомо нерабочим, а контроль `grep -q acceptance_presented` на нём
  зеленел. Адреса теперь отдаёт ОДИН источник — подкоманда `events.sh acceptance-ids
  <contract.json> [manual|all]`, — а образец собирает `jq`. Контроль проверяет, что образец
  парсится и совпадает с адресами журнала.

### Ужесточения v3.3.5 — круг 5: механизм вместо регулярки

Пятый круг панели (FIX-FIRST@0.96) показал, что два класса из круга 4 не устранены, а
переехали — третий раз подряд. Правки здесь меняют МЕХАНИЗМ, а не шаблон.

- **Вердикт берётся из МАШИННОГО артефакта, а не из прозы.** Разбор человеческого текста
  давал то ложный пропуск, то ложный отказ: якорь `^` отвергал каждый реальный `judge.md`,
  а проверка неоднозначности — 3 из 8 честных отчётов (их текст цитирует чужие вердикты
  в находках), то есть 37% ложных отказов на живом парке. Порядок теперь:
  (1) отчёт — JSON → `.verdict`; (2) рядом с markdown лежит `judge.json` → вердикт ИЗ НЕГО
  (`/finalize` и `plan-panel` пишут его всегда, значит боевой маршрут машинный целиком);
  (3) машинного артефакта нет → ПЕРВОЕ объявление и ПЕРВЫЙ токен в нём, без сверки по всему
  тексту. Источник записывается в событие полем `verdict_source`.
  Контроль — по КОРПУСУ реальных отчётов (`lib/fixtures/reports/`), а не по синтетике.
- **Рубильники надзора снимаются в снапшот** (`acceptance_enforce`, `state_files_enforce`)
  и читаются из журнала. Раньше они читались из окружения на финале: прогон стартовал
  с двумя кадрами приёмки, а `REDLOOP_ACCEPTANCE_ENFORCE=0 … run_done` закрывал его зелёным —
  класс «надзираемая сторона снимает надзор» переехал из payload в переменную окружения.
- **`run_start_missing` — без рубильника.** Строгость и требования живут в снапшоте `run_start`;
  читать здесь окружение значило бы отдать весь надзор одной переменной.
- **Исход прогона — закрытый enum `outcome`** (`success` | `failed` | `blocked` | `abandoned`),
  умолчание `success` записывается ЯВНО. До этого честно сдавшийся прогон не мог записать финал
  ВООБЩЕ: И8 требовал зелёного чекера, И9 — предъявления кадров, а у сдавшегося нет ни того,
  ни другого. Провал был неотличим от тишины, и самым дешёвым выходом для агента становилось
  вписать id кадров, которых он не показывал. И8/И9 спрашивают только с `outcome: success`.
- **Строка `RUN_DONE` в TG несёт приёмку и исход** — единственный канал, доходящий до владельца,
  больше не молчит о новом сигнале.

⚠ **Граница честности приёмки.** Журнал проверяет, что кадр НАЗВАН в финале, а не что владелец
его посмотрел и принял. Карточка говорит ровно это («названо в финале N из M») — она не вправе
утверждать больше журнала. Артефакта под предъявлением нет, в отличие от `fresh_check`, где есть
файл отчёта, его mtime, путь и sha256.

### Ужесточения v3.3.6 — круги 6–7: доставка, подлинность, адреса

- **Гарантии подлинности переехали ВМЕСТЕ с полномочием.** Когда авторитет вердикта перешёл
  к `judge.json`, все проверки (непустота, валидность, «не старее последней итерации») остались
  наложены на markdown: протухший `judge.json` со `SHIP` рядом со свежим отчётом закрывал прогон
  зелёным. Теперь машинный артефакт проверяется теми же правилами, а его `sha256` пишется
  отдельным полем `verdict_source_sha` (`report_sha` относится к markdown и о подмене авторитета
  не говорит ничего). Валидный и свежий артефакт БЕЗ вердикта — отказ, а не молчаливый возврат
  к разбору прозы.
- **Путь «отчёт сам JSON» падал.** Переменная объявлялась внутри чужой ветки, и под `set -u`
  `append` умирал кодом 1 вместо осмысленного отказа. Собственный документированный путь №1
  не был покрыт НИ ОДНИМ тестом: корпус состоит из markdown. Теперь покрыт.
- **Объявление ВЕРХНЕГО уровня главнее.** Разбор брал первое совпадение в файле, и отчёт
  «Ссылаюсь на прошлый verdict: SHIP … Вердикт: NEEDS-WORK» закрывал прогон зелёным по чужой
  метке. Сначала ищется объявление с начала строки, mid-line остаётся запасным (реальный
  `judge.md` пишет вердикт в середине строки).
- **Честный неуспех обязан ДОЙТИ до владельца.** `RUN-ABANDONED` внесён в `non_shadow_detectors`:
  это не эвристика, а факт из журнала — прогон сам объявил, что не сделал задачу. Лечили ложную
  тревогу (FRESH-CHECK-MISSING на честной сдаче) и чуть не вылечили доставку: `SILENCE` гасится
  наличием `run_done`, авто-нотификация выключена по умолчанию, и упавший прогон переставал
  доходить до человека вообще.
- **Исход и вердикт не противоречат.** `outcome != success` с зелёным `verdict` (например
  «SHIP + blocked») отвергается как `outcome_contradicts_verdict`: эту строку печатали
  и карточка, и улика детектора.
- **Адреса кадров приёмки уникальны.** Дубль `id` схлопывал гейт (разность массивов в jq удаляет
  ВСЕ вхождения, поэтому один предъявленный «57» закрывал произвольное число кадров), а карточка
  печатала «названо 2 из 2». Отказ `acceptance_ids_not_unique` на старте; тем же правилом ловится
  столкновение явного `#1` с автоадресом позиции.
- **Enum'ы печатаются из словаря, а не прозой.** Промпт брал список исходов и вердиктов текстом;
  машинный контроль дрейфа расширен с одного поля на все (`fresh_ok_verdicts`,
  `run_done_outcomes`) через маркеры `<!-- <ключ>: … -->` в обеих доках.

### Миграция смысла `iters`

| версия | `iters` в `run_done` | `iters_claimed` |
|---|---|---|
| до v3.3 | самоотчёт раннера | — |
| с v3.3 | счёт по событиям `iter_done` | самоотчёт раннера |

С v3.3.1 финал несёт поле `contract_version`. Агрегируя парк прогонов, сравнивать `iters`
можно только внутри одной версии — иначе тренд «автономность выросла» получится из смены
единицы измерения.

### Коды возврата `events.sh append`
| код | значение |
|---|---|
| 0 | записано (или идемпотентный no-op) |
| 1 | невалидный вход: enum, обязательное поле, секрет, запрещённое поле |
| 4 | **отказ по политике журнала** — причина машинная, в stderr `reason=<код>`: `no_iterations_logged`, `run_done_already_recorded`, `run_start_missing`, `snapshot_override_attempt`, `outcome_not_in_enum`, `outcome_contradicts_verdict`, `acceptance_ids_not_unique`, `state_files_missing`, `fresh_check_missing`, `fresh_check_not_green`, `fresh_check_stale`, `acceptance_not_declared`, `acceptance_not_itemized`, `acceptance_not_presented`, `acceptance_presented_unknown` — каждый дублируется событием `runner_error/journal_policy_reject` |

## Доставка финала
`run_done` может сам звать `escalate.sh RUN_DONE` (`REDLOOP_AUTO_FINAL_NOTIFY=1`).
Вызов идёт **после снятия лока и вне `append()`**: `escalate.sh` пишет своё событие через этот
же `events.sh`, и вызов из-под лока молча провалился бы на каждом прогоне.
В сообщение уходят только машинные поля (вердикт, DoD, итерации) — свободный текст агента во
внешний канал не отправляется. По умолчанию выключено, пока путь не подтверждён живым прогоном.

## Сторож и корроборация (v3.1)
`lib/watch.sh` (джоба `com.redloop.watch`, каждые 15 минут) обходит реестр, читает журналы и
пишет находки в `runs/<id>/alerts.jsonl` — **свой** файл: писатель `events.jsonl` по контракту один.
Эскалацию сторож шлёт с `REDLOOP_ESCALATE_NO_EVENT=1`, то есть события в чужой журнал НЕ пишет:
иначе запись сдвигала бы `.[-1].ts`, на который опирается сам детектор тишины, и сигнал стирал бы
себя. Дедуп тревог считает ДОСТАВЛЕННЫЕ, а не записанные: недоставленная тревога повторяется на
следующем обходе, а обход с недоставками возвращает код 3.
Находки тихих детекторов сторож ФИКСИРУЕТ (это материал для калибровки) и не доставляет —
иначе тихий детектор никогда не набрал бы чисел для выхода из тихого режима.

**Формат `alerts.jsonl`: ОДНА строка на (прогон × детектор).** Повтор той же находки на следующем
обходе не добавляет строку, а увеличивает `seen_count` и обновляет `last_ts`; подавления копятся
в `suppressed_count`. Первая версия писала строку на каждый обход — за сутки 100 одинаковых записей
на прогон и рост без предела. Повтор одного факта не улика, а шум.
Поля: `detector, severity, evidence, ts, last_ts, seen_count, suppressed_count, shadow,
delivered, delivered_ts?, false_positive?`.

**Калибровка читает `alerts.jsonl`, а не события журнала.** До этого она считала `detector_fire`
в `events.jsonl`, которых не пишет НИКТО: находки живут у сторожа. Значит `fires` был вечным нулём,
`fp_rate` не считался, и `exit_shadow_allowed` не мог стать истинным ни при каком числе прогонов —
порог был недостижим по построению. Считаются НАХОДКИ (строки), а не повторы.

⚠ **Тишина в журнале ≠ смерть прогона.** Первое боевое применение дало ложную тревогу: прогон
«молчал» 192 минуты, а на деле работал — коммитил и правил файлы, просто не вёл журнал.
Журнальная тишина здесь прокси, а не результат. Поэтому `SILENCE` перед эскалацией
подтверждается внешним признаком жизни (свежие правки в дереве проекта); есть признаки жизни →
тревога подавляется, пишется в `alerts.jsonl` с `suppressed:true` и считается отдельным числом.
Подавленные не исчезают из отчёта: «0 тревог» без «сколько подавлено» скрывало бы, что сторож
срабатывает вхолостую.
